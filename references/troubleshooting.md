## 정답 순서 — 이대로만 하면 된다

```bash
NAME=<이름>

# ① Tripo3D — Format **GLB** · Texture **2K** · Ultra Mesh **OFF** · T-Pose **ON**
#    프롬프트에 "legs together, feet touching, arms straight out horizontally" 를 넣는다
mv ~/Downloads/${NAME}_raw.glb outputs/tripo3d.ai/

# ② 정규화 — 🛑 리깅 **전에**. 정면은 -Y 그대로 둔다(ARP 규약)
blender --background --python .claude/skills/model/scripts/normalize_for_godot.py -- \
  outputs/tripo3d.ai/${NAME}_raw.glb outputs/${NAME}/${NAME}_norm.blend \
  --kind human --height 1.8 --triangles 20000

# ③ ARP 자동 리깅 — 🛑 --background 를 붙이지 않는다(창이 뜨지만 알아서 닫힌다)
blender outputs/${NAME}/${NAME}_norm.blend \
  --python .claude/skills/model/scripts/arp_autorig.py -- outputs/${NAME}/${NAME}_rig.blend

# ④ Mixamo 본 이름으로 export
blender --background --python .claude/skills/model/scripts/arp_export_mixamo.py -- \
  outputs/${NAME}/${NAME}_rig.blend outputs/${NAME}/${NAME}.fbx

# ⑤ rest pose 보정 리타게팅 — 🛑 액션을 그냥 복사하면 팔이 만세가 된다
blender --background --python .claude/skills/model/scripts/retarget_to_arp_rig.py -- \
  outputs/${NAME}/${NAME}.fbx game-assets/animations/default \
  outputs/${NAME}/${NAME}_anim.blend

# ⑥ GLB — 본 감축·root motion 제거·정면 교정·텍스처 리사이즈를 한 번에
blender --background --python .claude/skills/model/scripts/export_godot_glb.py -- \
  outputs/${NAME}/${NAME}_anim.blend outputs/${NAME}/${NAME}.glb \
  --kind human --bones 25 --texture 1024

# ⑦ 완료 게이트 — 🛑 종료 0 이 아니면 Godot 에 넣지 않는다
python3 .claude/skills/model/scripts/verify_godot_glb.py \
  outputs/${NAME}/${NAME}.glb --bones 25 --kind human --tris 20000
```

### 🛑 순서를 바꾸면 안 되는 세 곳

| 순서 | 바꾸면 |
|---|---|
| **정규화 → 리깅** | 리깅 후 스케일을 바꾸면 본 길이와 액션 위치 키가 어긋난다 |
| **애니 → 본 감축** | 감축이 먼저면 Mixamo 의 어깨·목 트랙이 갈 곳을 잃어 **그 회전이 사라진다** |
| **리깅·애니 → 정면 교정** | 교정이 먼저면 ARP 가 뒤통수를 얼굴로 착각해 **몸통·머리만 반대로** 심는다 |

### 눈으로 확인할 것 (자동 검증이 못 잡는다)

1. **정면 렌더** — 얼굴·가슴·발끝이 **같은 방향**인가
2. **측면 렌더** — 몸통과 다리가 같은 방향인가
3. **애니 재생 중 크기** — rest 만 재면 폭발을 놓친다

## 사고 1. 캐릭터 크기 — 1.2cm 와 270m 거인

**두 번 연달아 터진 사고다. 두 번째는 첫 번째를 덮은 값 때문에 났다.**

### 1차 — 1.2cm

```
Blender 월드에서 이미 1.8m 인데
glTF 노드에 scale 0.018 이 또 실려 → Godot 이 한 번 더 곱해 ≈ 0.03m
```

메시·리그의 변환이 **glTF 루트 노드에 실려 나가** Godot 이 다시 곱했다.

### 2차 — 270m (더 나쁘다)

1차를 `.import` 의 **`root_scale=150`** 으로 덮었다. 그 뒤 GLB 를 근본 해결해 1.8m 로
만들었는데 **150 이 그대로 남아** `1.8 × 150 = 270m` 가 됐다. 카메라 직교
`size=22.5` 기준 **화면의 12배** — 화면이 텍스처 한 조각으로 가득 찼다.

> **증상을 덮은 값은 근본을 고친 뒤 반드시 되돌려야 하고, 되돌리는 것을 잊는다.**
> 그래서 애초에 덮지 않는다 → CLAUDE.md "근본 원인을 고친다".

### 해결

`normalize_for_godot.py` 가 **모든 변환을 정점·본에 구워** 루트를 `scale 1 · rot 0` 으로
만든다. `.import` 의 `nodes/root_scale` 은 **반드시 `1.0`**.

### 재발 방지

`verify_godot_glb.py` 가 **루트 노드의 scale·translation** 을 검사한다.

## 사고 2. 캐릭터가 누워 있다 — 메시와 리그의 축이 다르다

**진단이 두 번 뒤집힌 사고다.**

### 처음 내려진 진단 (부분적으로 틀렸다)

> "메시 정점 좌표 자체가 거꾸로 저장되어 있다. 노드 변환이 아니라 메시 데이터를
> 편집해야 고쳐진다."

### 실제 원인 — 실측

| 대상 | 데이터 축 | 오브젝트 회전 | 결과 |
|---|---|---|---|
| `human` 메시 | **Y-up** (Tripo 원본) | X +90° | ✅ 똑바로 섬 |
| `Armature` | **Z-up** (Mixamo FBX) | X +90° | ❌ **90° 더 돌아 누움** |

**메시와 스켈레톤이 서로 다른 축 규약인데 같은 회전을 걸어서 하나만 맞았다.**
게다가 아마추어에 `scale 0.01` 이 살아 있어 단위계까지 섞였다.

회전은 **정상적인 Z-up→Y-up 변환**이었다. 틀어진 것은 **위치**였고, Blender 에서
Z 로 올려 Apply 하면 풀린다. "메시 데이터를 편집해야 한다" 는 과한 결론이었다.

### 뿌리 — 두 좌표계가 섞인다

| | 축 | 단위 |
|---|---|---|
| **Tripo3D 메시** | Y-up | 1.0 정규화 |
| **Mixamo 리그** | Z-up | **cm** (Hips 63.49) |

### 해결 — 규약을 파이프라인 앞에 둔다

> **Tripo3D 다운로드 직후, 리깅 전에, 키 1.8m · 발바닥 원점 · Z-up · scale 1 · rot 0
> 으로 정규화한다.**

**리깅 전**이 핵심이다. 이미 리깅된 파일을 `--rigged` 로 사후 구제하면 rest 는
고쳐지지만 **메시와 리그의 정합성은 복원되지 않는다** — `male.blend` 가 그렇게
실패했다(rest 1.8m 정상, 애니 재생 시 4.9~8.6m).

## 사고 3. 뒤로 걷는다 — 정면이 Godot 과 반대

### 증상

이동은 정확하다. 위 화살표 → 위로 간다. **그런데 얼굴이 뒤를 향해 뒷걸음질한다.**

### 원인

| | |
|---|---|
| 발가락 방향 | Blender **−Y** (0.190 vs 뒤꿈치 0.127) |
| glTF 변환 | Blender −Y → **+Z** |
| Godot 표준 forward | **−Z** |

**Tripo3D 원본은 −Y 정면으로 나온다.** glTF 익스포터에는 forward 옵션이 없어
Blender +Y 가 그대로 −Z 가 된다.

⚠️ **`assets-3d.md` 의 "−Y forward 로 내보낸다" 와 혼동하지 말 것** — 그것은 **FBX
익스포터의 `axis_forward` 설정**이다. **포맷이 다르면 규약도 다르다.**

### 해결 — 에셋에서 고친다

🛑 **Godot 에서 `rotation.y += PI` 로 덮지 않는다.** 캐릭터마다 반복되고,
`BoneAttachment3D` 로 붙이는 무기까지 전부 따라 틀어진다.

`export_godot_glb.py` 가 발가락으로 판별해 180° 돌린다(`--no-face-godot` 로 끌 수 있다).

### 입력 코드는 건드리지 않았다

```gdscript
var input := Input.get_vector("ui_left", "ui_right", "ui_up", "ui_down")
var dir := Vector3(input.x, 0.0, input.y)   # ui_up → y=-1 → 월드 -Z = 화면 위
```

**부호를 뒤집으면 모델 문제를 입력으로 덮는 꼴이 된다.**

## 사고 4. 몸통만 거꾸로 — 정면 교정을 리깅 전에 했다

**사고 3 을 고치다가 만든 2차 사고. 순서 하나가 틀렸다.**

### 증상 — 이것이 원인을 정확히 가리킨다

```
다리 · 무릎 · 발  → 방향이 맞다 ✅
허벅지 · 엉덩이 · 등 · 머리 → 180° 뒤집혀 있다 🛑
```

### 원인

**ARP Smart 는 캐릭터가 −Y 를 향한다고 전제**하고 마커에서 리그를 만든다.
정면 교정을 **리깅 전**에 넣었더니 ARP 가 **뒤통수를 얼굴로 착각**해 몸통·머리 본을
반대로 심었다. **다리는 좌우 대칭이라 정상으로 보여** 원인을 찾기 어려웠다.

### 두 증상은 구별된다

| 증상 | 원인 | 대처 |
|---|---|---|
| **통째로** 뒤를 본다 | 정면 교정을 **안 함** | export 가 처리 |
| **몸통만** 뒤집힘 | 정면 교정을 **리깅 전에** 함 | **리깅부터 다시** |

### 해결 — 정면 교정은 리깅·애니가 **끝난 뒤**

| 단계 | Blender 정면 |
|---|---|
| 정규화 · 리깅 · 애니 | **−Y 그대로** (ARP·Mixamo 규약) |
| **export 직전** | **+Y 로 180° 회전** → glTF −Z |

`normalize_for_godot.py` 는 정면을 **확인만** 하고, `export_godot_glb.py` 가 돌린다.

## 🛑🛑 판단 오류 — "ARP 는 자동화 불가" 오판

**기술적 사고가 아니라 내가 내린 잘못된 결론이다. 가장 크게 반성할 지점이다.**

### 무슨 일이 있었나

`blender **--background**` 에서 ARP 의 첫 연산자가 죽었다:

```
bpy.ops.id.get_selected_objects() → set_selection_filters()
  → space_view3d = [i for i in current_area.spaces if i.type == "VIEW_3D"]
AttributeError: 'NoneType' object has no attribute 'spaces'
```

이것을 보고 **"ARP 는 3D 뷰 area 를 직접 참조하므로 자동화가 구조적으로 불가능하다.
사람이 GUI 에서 직접 리깅해야 한다"** 고 결론내고 사람에게 작업을 넘겼다.

사람 개발자가 **"다른 AI 는 잘 해왔다. 왜 안 된다고 하느냐"** 고 지적했고,
다시 확인한 결과 **GUI 모드로 띄우면 그대로 동작**했다.

### 무엇을 잘못했나 — 일반화의 오류

| | |
|---|---|
| 관찰한 사실 | **`--background` 하나**에서 죽는다 |
| 내린 결론 🛑 | "ARP 는 자동화 불가" ← **한 실행 모드의 제약을 도구 전체로 확대** |
| 실제 ✅ | GUI 모드에는 `area` 가 있어 **전부 정상 동작** |
| **가장 나쁜 것** | **해법이 [SKILL.md](../SKILL.md) ④-A 5번에 이미 적혀 있었다.** 읽고도 쓰지 않았다 |

### 동작하는 방법

```bash
# 🛑 --background 를 붙이지 않는다. 창이 뜨지만 스크립트가 끝내고 닫는다
blender outputs/<NAME>/<NAME>_norm.blend \
  --python .claude/skills/model/scripts/arp_autorig.py -- outputs/<NAME>/<NAME>_rig.blend
```

```python
def run():
    w  = bpy.context.window_manager.windows[0]
    a  = next(x for x in w.screen.areas if x.type == 'VIEW_3D')
    rg = next(r for r in a.regions if r.type == 'WINDOW')
    with bpy.context.temp_override(window=w, area=a, region=rg):
        ...  # ARP 연산자가 전부 동작한다
    bpy.ops.wm.quit_blender()
    return None

bpy.app.timers.register(run, first_interval=2.0)   # 창이 준비될 때까지 미룬다
```

### 막히면 이 순서로 확인한다

1. **실행 모드를 바꿔 본다.** `--background` 가 막히면 **GUI 모드**를 시도한다.
2. **스킬 문서를 먼저 다시 읽는다.** 답이 이미 있을 수 있다.
3. **"불가능" 이라고 쓰기 전에 한 번 더 의심한다.**
   **한 방법이 막힌 것과 도구가 불가능한 것은 다르다.**

## 사고 5. 애니 재생 시 캐릭터가 폭발

### 증상 — 검증은 통과한다

| 상태 | 키 |
|---|---|
| rest (정지) | **1.800 m** ✅ ← 검증이 본 것 |
| idle 재생 | 4.91 m 🛑 |
| walk / attack / death | 5.8 ~ 8.6 m 🛑 |

### 원인 둘

**① 단위 불일치 — 117배**

| | Hips rest 높이 | 단위 |
|---|---|---|
| 우리 리그(정규화됨) | `0.894` | **m** |
| Mixamo 애니 원본 | `105.246` | **cm** |

액션의 location 키는 본 로컬 값이라 아마추어 scale 과 무관하게 남는다. 보정 없이
붙이면 Hips 가 "148 **cm**" 가 아니라 "148 **m**" 위로 올라간다.

**② rest pose 불일치 (더 근본적)**

ARP 리그는 **이름만 Mixamo 이고 rest pose(본 방향·roll)가 다르다.** 액션을 그대로
복사하면 안 되고 **리타게팅**해야 한다 → `retarget_to_arp_rig.py`(⑤).
이 단계를 빼면 **팔이 전부 만세**가 된다.

### 해결

- `export_godot_glb.py` 가 Hips rest 높이 비율로 **단위 보정**
- `retarget_to_arp_rig.py` 로 **rest pose 보정** — 정답 순서 ⑤
- `verify_godot_glb.py` 에 **애니 translation 단위 검사** 추가

### 🛑 검증의 빈틈 — 아직 남아 있다

**rest bbox 만 보면 애니 폭발을 통과시킨다.** GLB 만으로 애니 적용 크기를 알려면
스키닝을 시뮬레이션해야 해서, 지금 게이트는 translation 키 크기로 간접 판단한다.
**새 캐릭터는 Blender 로 몇 프레임 샘플링해 눈으로 확인한다.**

## 사고 6. 걸을 때 공중으로 떠오른다 — root motion

### 증상

| 애니 | 발바닥 z 범위 |
|---|---|
| idle | +0.089 ~ +0.105 ✅ |
| run | +0.011 ~ +0.212 ✅ |
| **walk** | **+0.211 ~ +1.663** 🛑 (1.45m 부양) |

### 원인

Mixamo `walk` 는 **in-place 가 아니라 전진하는 애니**다. Godot 은 이동을 코드
(`CharacterBody3D`)가 하므로, 애니에 남은 전진이 겹쳐 캐릭터가 밀려나거나 떠오른다.

### 해결 — drift 로 판별한다

첫 프레임과 마지막 프레임의 **차이(drift)** 가 큰 축이 전진이다.
**상하 바운스는 왕복이라 drift 가 0 에 가까워** 그대로 살아남는다.

```
walk: root motion 제거 — axis1(drift 1.65m)
→ 발바닥 +0.120 ~ +0.254 (13cm 자연스러운 상하)
```

### ⚠️ 이동 애니에만 적용한다

`death` 처럼 **쓰러지며 자리를 옮기는** 동작은 그 변위가 연출이다. 제거하면 오히려
발바닥이 +0.99m 로 떠올랐다. 대상은 **`walk` · `run`** 만.

## 사고 7. 검이 예산을 독식해 캐릭터가 뭉개졌다

### 증상 — 총합은 통과한다

```
[OK] 삼각형 4,798 ≤ 예산 6,000
```

그런데 그 안의 분포가:

| 프리미티브 | 대상 | 삼각형 | 비중 |
|---|---|---|---|
| prim0 | **캐릭터 본체** | **234** | 4.9% |
| prim1 | **검** | **4,564** | **95.1%** |

**캐릭터가 234 삼각형** — 규격(LOD0 3,000~6,000)의 1/20 이라 사람 형체가 안 나온다.

### 원인 — 비례 배분의 함정

Decimate 를 **원본 폴리곤 비례**로 배분했다. 검이 원본 970,514(95%)라 예산의 95% 를
검에 줬다 — **가장 조잡한 메시가 예산을 독식**하는 구조였다.

### 해결 셋

1. **균등 상한 배분** — 예산÷메시 수를 상한으로, 작은 메시는 그대로 두고 남은 예산을 큰 메시에
2. **검증에 프리미티브 분포 검사** — 하나가 70% 를 넘으면 실패
3. **정규화 로그가 메시별 삼각형 출력**

### 🛑 더 근본적으로 — 무기는 분리한다

무기를 캐릭터 메시에 합치면 **MMORPG 에서 교체할 수 없다.** 무기는
`BoneAttachment3D` 로 손 본에 붙이는 **별도 에셋**이다.

```bash
# 캐릭터 — 무기 제외
--exclude weapon
# 무기 — 따로. prop 은 --height 를 줘야 크기가 맞는다(안 주면 4cm 검이 나온다)
--only weapon --kind prop --height 1.0 --no-center
```

**애초에 Tripo 프롬프트에서 무기를 빼고 따로 생성하는 것이 최선이다.**

## 조용히 실패하는 함정 12가지

**전부 오류를 내지 않는다.** 직접 구현할 때 반드시 알아야 한다.

| # | 함정 | 증상 | 대응 |
|---|---|---|---|
| 1 | **숨겨진 오브젝트는 `select_set(True)` 가 무시된다** | `transform_apply` 가 `{'FINISHED'}` 인데 적용 안 됨 | `hide_set(False)` 를 먼저 |
| 2 | **애니가 붙으면 `transform_apply` 가 거부** | 위와 같은 잔존 | 액션을 떼고 굽고 되돌린다 |
| 3 | **`data.transform()` 은 rest 만 바꾸고 pose 는 안 바꾼다** | 키 1.0 → **89.3** (100배) | 연산자에 맡긴다 |
| 4 | **부모·자식을 함께 변환하면 이중 적용** | 1.8 을 노렸는데 **10.03** | 부모를 끊고 작업 후 복원 |
| 5 | **`evaluated_get()` bbox 는 흔들린다** | 스케일 맞춘 직후에 재도 다른 값 | 원본 메시(`o.bound_box`)로 잰다 |
| 6 | **`match_to_rig` 후 EDIT_ARMATURE 로 남는다** | 다음 연산자가 전부 `poll() failed` | Object 모드 복귀 |
| 7 | **`img.scale()` 만으로는 GLB 에 반영 안 됨** | 4096→1024 했는데 파일이 20MB | `scale()` 뒤 **`pack()`** |
| 8 | **`open_mainfile()` 직후 `has_data` 가 False** | 텍스처 리사이즈가 통째로 건너뛰어짐 | `has_data` 로 거르지 않는다 |
| 9 | **GLB 애니는 기본이 루프 없음** | idle 이 2초 만에 멈춘다 | `loop_mode = LOOP_LINEAR` |
| 10 | **slotted action(4.4+)은 slot 을 안 잡으면 평가 안 됨** | 정적 T-포즈 | `animation_data.action_slot` |
| 11 | **Decimate 하드 리밋** | 예산에 도달 못 하고 멈춘다 | 분리 조각의 최소 합. **형상 확인 후 예산을 올린다** |
| 12 | **`retarget_to_arp_rig.py` 의 행동 목록이 2.5D 시절** | `attack` 이 빠진 채 "성공" | 폴더의 `.fbx` 를 전부 처리하도록 수정됨 |

## 내가 저지른 진단 오류

**기술 문제와 별개로, 내가 잘못 판단한 것들. 같은 실수를 반복하지 않기 위해 남긴다.**

| # | 오판 | 실제 | 교훈 |
|---|---|---|---|
| 1 | **"ARP 는 자동화 불가"** | `--background` 만의 제약. GUI 모드로 동작 | **한 방법이 막힌 것 ≠ 도구가 불가능한 것** |
| 2 | **"카메라가 +45° 라 하늘을 본다"** | `.tscn` 의 `Transform3D` 12개 값은 **행(row)** 인데 열로 읽었다. 인스펙터의 −45° 가 맞았다 | **포맷의 저장 순서를 확인하고 계산한다** |
| 3 | **"애니가 폭발한다"(2.7~4.3m)** | Blender 임포터가 만든 **위젯 메시**가 bbox 를 오염시켰다. 캐릭터는 정상 | **측정 대상을 한정한다**(스킨된 메시만) |
| 4 | **"본 감축이 크기를 망가뜨렸다"** | 감축 없이도 같은 값. 원인은 3번 | **변인을 하나씩 제거해 확인한다** |
| 5 | 검증 게이트가 **rest 만 보고 통과**시켰다 | 애니 재생 상태를 안 봤다 | **게이트가 못 보는 축을 의식한다** |

### 공통 교훈

> **"통과했다" 는 "그 검사를 통과했다" 는 뜻이지 "올바르다" 는 뜻이 아니다.**
> 자동 검증 9개를 다 통과하고도 캐릭터가 234 삼각형이었고, 애니를 켜면 폭발했고,
> 뒤로 걸었다. **마지막에는 반드시 눈으로 본다.**
